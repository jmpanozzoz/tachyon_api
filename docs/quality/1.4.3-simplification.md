# 1.4.3 simplification: initial analysis and EGM review hypothesis

Author: Juan Manuel Panozzo Zenere

Date: 2026-11-06

Baseline: `f26f6060e7567260763e20cf09f7537d7f56af40`, version 1.4.2

Status: implemented candidate after user approval and seven-lens Goldfish review.
The observations below preserve the initial baseline. See the
[implementation/evidence index](../audits/1.4.3/README.md) for each item's outcome.

## Proposed scope

Make 1.4.3 a small compatibility-focused release that removes duplicated request
handling, unused metadata and inconsistent registration state. Keep the public
Python API, Starlette, msgspec, the default server and installation behavior;
accept performance claims only after comparable baseline/candidate measurements.

The strongest immediate opportunities are middleware consistency, predictable
route registration and repeated validation work. Removing files alone does not
establish a faster or more stable framework. Cython removal and direct transport
retirement already shipped; they are not new 1.4.3 work.

## Findings and proposed deletions

Priority P1 means address correctness or verification before release. P2 means a
bounded candidate for this patch. P3 means defer unless a small isolated change
has clear value. These are engineering priorities, not vulnerability ratings.

### S01 — P1: one middleware registration and ordering policy

**Observed:** [Tachyon.add_middleware](../../tachyon_api/app/__init__.py) writes
both Starlette's middleware list and [MiddlewareStack](../../tachyon_api/app/_mw_stack.py).
The [Starlette helper](../../tachyon_api/middlewares/core.py) rebuilds its stack
on each addition; the HTTP stack is built separately on demand. Registering A
then B produces HTTP `A → B` and WebSocket `B → A`. The probe records five
constructor calls for those two registrations plus first HTTP/WS use.

**Proposal:** use one registration list and one explicit order for protocol
dispatch. Prefer one outer user middleware chain around HTTP/WS/lifespan
dispatch if compatibility permits; avoid copying user middleware into two
independently managed stacks. Preserve HTTP order as the compatibility starting
point and review the change to WS/lifespan behavior explicitly.

**Benefit:** remove duplicated state, repeated constructors and protocol-specific
surprises. Middleware does not currently execute twice on each HTTP request;
this is not evidence of a 2× speed opportunity.

**Counterargument and checks:** middleware constructors may own state, and
protocol order can affect auth, logging and resource lifetime. Verify order,
instance identity, HTTP/WS/lifespan behavior, errors and mounted applications.
Define whether mutation after startup remains supported before removing stack
invalidation. Do not silently reverse HTTP order in a patch.

### S02 — P1: predictable documentation registration

**Observed at baseline:** `ASGIEntry` (removed in the candidate) checks docs setup
on every scope; [DocsRoutes.setup](../../tachyon_api/app/_docs_routes.py) adds
four routes on the first scope. A user-defined `GET /docs` becomes two registry
entries and serves framework HTML instead of the original JSON. The trie
replaces its handler, while [RouteRegistry](../../tachyon_api/app/_registry.py)
appends another entry. Setup marks itself done before installation completes.

**Proposal:** validate docs path conflicts and establish one explicit point for
registration. Remove silent overwrites and partial-setup state. Move the setup
check out of steady-state dispatch when possible, while retaining applications
that are served without lifespan. Keep trie, registry and schema consistent.

**Benefit:** fewer hidden mutations and less disagreement between CLI
introspection and execution. Removing one branch alone is a small performance
change, not a reason for a broad app rewrite.

**Counterargument and checks:** config can be changed before serving and existing
users may register reserved URLs. Define precedence or a clear registration
error with a migration note. Test conflicts, failed setup, custom docs URLs,
mounted root paths and requests with lifespan disabled. Do not make lifespan
mandatory just to eliminate lazy initialization.

### S03 — P2: delete metadata and adapters with no repository consumers

Repository searches found assignments but no reads of
`ParamDescriptor.dep_is_async` in [compiler.py](../../tachyon_api/processing/compiler.py)
and `CallableFactory._resolve_dep` in
[the callable factory](../../tachyon_api/processing/dependencies/_callable_factory.py).
The callable factory resolves through `_resolve_callable`; the similarly named
field in `ClassFactory` is used and must remain.

`OverrideLookup.lookup` has no call sites; active resolution uses
`get_override`. `MiddlewareStack.middlewares` also has no repository consumers.
Remove these unused members and their constructor plumbing. They are internal
candidates, not proof that every external consumer ignores private modules.
Keep public exports and use the existing DI/compiler suites to check behavior.
Expected benefit is smaller state and less misleading code; no speed claim yet.

### S04 — P2: remove unreachable body-error handling

[BodyExtractor._decode](../../tachyon_api/processing/_extractors/body.py) catches
`msgspec.DecodeError` before `msgspec.ValidationError`. The latter inherits the
former in the installed 0.19.0 and the versioned
[msgspec API documentation](https://github.com/msgspec/msgspec/blob/0.19.0/docs/source/api.rst).
The invalid-type probe returns the existing `Invalid JSON body: ...` payload and
never invokes `_msgspec_validation_response`.

For a subtractive patch, remove the unreachable catch/helper and retain the
current error contract. Reversing catch order would change payloads; that is a
separate behavior decision and does not automatically produce field-level
errors. Check malformed JSON and valid JSON with wrong types independently.

### S05 — P2: one implementation of response headers and sending

[TachyonJSONResponse](../../tachyon_api/responses/_json_response.py) and
[TachyonBytesResponse](../../tachyon_api/responses/_bytes_response.py) repeat
status handling, content-length lookup, header construction, HEAD behavior,
message copying and background execution. The main difference is whether
content must first be encoded.

Share that implementation while retaining both public classes, signatures and
encoders. This removes duplicate fixes and reduces drift risk. Compare subclass
behavior and benchmark before selecting inheritance or a helper: another call
on every response can offset a small local optimization. Preserve per-response
headers, HEAD, 204/304 and background-task contracts. Keep
`ResponseProcessor.send_response` as the transmission/stream-cleanup boundary.

### S06 — P2: make bounded receive the body-limit authority

`BodySizeChecker` (removed in the candidate) checks
the header and post-read length, while
[TachyonScope._bounded_receive](../../tachyon_api/processing/scope.py) already
checks declared size and cumulative bytes for JSON, Request, forms and files.
The JSON path maintains two limit holders and overlapping checks.

Evaluate removing the JSON-only checker and retaining the shared receive guard.
This reduces policy duplication; it must preserve early rejection, the existing
422 contract, HTTP/1 connection retirement, streamed-body limits and HTTP/2
header behavior. Confirm every body access uses the bounded receive before
deleting anything. Keep upload cleanup and cancellation shielding intact.
Do not trade early rejection for reading an oversized body into memory.

### S07 — P2 investigation: avoid repeated DI graph validation

[The resolver](../../tachyon_api/processing/dependencies/_resolver.py) calls
`prepare_dependency` before checking already resolved instances, including
singleton hits. The probe and existing shared-graph test show **15 binding
visits per cached resolution of a 15-node graph**, on three repeated calls.
`Depends(Class)` also enters callable resolution before class resolution.
Registration already prepares signatures and bindings.

Investigate reusing validated plans when the provider graph and overrides have
not changed, rather than repeating whole-graph traversal at every nested
resolution. Instrument graph visits and actual workload CPU cost first.

**Strongest objection:** revalidation currently prevents unsafe singleton capture
when overrides change, including changes during an awaited construction. A
global plan cache or a request memo without invalidation can revive repaired
defects. Plain mutable override dictionaries and replacement of that dictionary
make invalidation nontrivial. A revisioned registry is a design option, not an
approved new abstraction. If a smaller safe change is not demonstrated, keep
the existing implementation for 1.4.3. Do not ship a second DI engine.

### S08 — P2 design candidate: delegate CORS to the existing dependency

[The custom CORS implementation](../../tachyon_api/middlewares/cors.py) maintains
159 lines of protocol logic already supplied by Starlette. With an allowed
origin but disallowed method/header, the probe returns 200 for Tachyon and 400
for Starlette. Tachyon emits separate `Vary` fields; Starlette combines them.
Repeated `Vary` fields are not, by themselves, proof of invalid HTTP.

Evaluate a compatibility wrapper around Starlette's CORS, retaining the public
import and intended defaults. Check the
[versioned middleware documentation](https://github.com/kludex/starlette/blob/1.10.0/docs/middleware.md).
A direct alias changes defaults and preflight behavior; it is not an automatic
patch-safe replacement. Browser enforcement still depends on returned CORS
headers: the observed 200 does not prove an authorization bypass. Gate this
candidate on a behavior matrix for methods, headers, credentials, cookies,
origin echo, `Vary`, errors and unsupported origins. Defer if compatibility
requires recreating the custom implementation inside the wrapper.

### S09 — P2 small cleanup: make cache configuration intent explicit

[The app](../../tachyon_api/app/__init__.py) treats `set_cache_config` as an
optional import, but [the package root](../../tachyon_api/__init__.py) imports
cache utilities unconditionally. This fallback does not provide a usable
cache-free package mode. Remove the fake optional-import branch, while deciding
separately whether invalid configuration should continue to log and proceed.

[Cache decorators](../../tachyon_api/cache.py) capture configuration at
decoration time. `Tachyon(cache_config=...)` also changes the global default for
future decorations, rather than rebinding existing ones. Preserve that existing
contract in this patch and keep explicit `cache(config=...)` for isolation.
Removing global helpers would break public imports. The bounded in-memory
backend and external-I/O offloading already exist and should remain.

### S10 — P1 verification: one supported, recorded development baseline

[CI](../../.github/workflows/ci.yml) and
[local release](../../scripts/local_release.py) install allowed dependency
ranges with pip/uv; they do not reproduce `poetry.lock` exactly. The local
release runner rejects unsupported interpreters, but
[quality_cycle](../../scripts/quality_cycle.py) has no equivalent early guard.
The checkout `.venv` mismatch made this visible during the analysis.

Provide one documented supported development setup, fail clearly on unsupported
Python in quality tooling, and distinguish locked/minimum-dependency checks
from current allowed-resolution checks. Share a small dependency constraints
input where useful, retaining separate results. Do not pin all library consumers
to one development environment or add a new environment orchestration system.
The deprecation warnings from Starlette/httpx, Typer/Click and example datetime
calls belong in compatibility follow-up, not an unreviewed bulk dependency bump.

### S11 — P3: merge thin internal collaborators selectively

`ASGIEntry`, `RouteRegistry`, `OverrideLookup` and the two handler factories
offer small, concrete places to consider functions or direct app-owned state.
Keep objects that own meaningful lifetimes or state: trie, scope, dependency
resolver, lifecycle manager and schema generator. There is no demonstrated
benefit in flattening every small module or deleting the no-parameter fast path.

Start only where S01–S09 already remove indirection. Keep module import surfaces
if required and compare startup, allocations and ASGI costs. Avoid a broad
facade rewrite that makes the patch harder to review than the original code.

### S12 — P3: installation, build and evidence maintenance

- Uvicorn, httptools and Typer remain mandatory install dependencies, but CLI
  code is outside the normal ASGI import path. Splitting `server`/`cli` extras
  could reduce installation weight; changing default installations breaks
  expectations and belongs in a future minor release with a transition plan.
- `setup.py` uses setuptools and Poetry metadata after native compilation was
  retired. Evaluate a single backend separately, validating entry points,
  extras, license metadata, wheel/sdist inventories and source rebuilds. The six
  release/check scripts total 478 lines; their boundaries are useful and do not
  justify a replacement release framework.
- Keep the portable-wheel/source-hash checks, sdist rebuild, installed-origin
  checks and upload hash verification. Retain the empty deprecated `[fast]`
  extra and small server compatibility facade. Their deletion brings little
  runtime value and removes installation/import compatibility.
- CLI templates repeat public API guidance. Consolidating their source of truth
  may reduce documentation drift, but deleting commands or scaffolding does not
  speed up HTTP requests. Keep managed-section preservation and read-only lint.
- Preserve historical audits and hashes. Provide a short release index instead
  of deleting evidence or repeating historical claims as current guarantees.
  Documentation cleanup affects maintenance, not framework throughput.

## Coverage of the remaining areas

| Area | Assessment and boundary |
| --- | --- |
| Routing | Keep the trie and 1.4.2 suffix pruning. No replacement router justified by this review; preserve Unicode, ambiguous fallback, static 405 precedence and mount parameters. |
| Parameter extraction | Remove proven duplicates first; retain per-kind handling where wire semantics differ. Avoid a new generic parser framework. |
| OpenAPI | Address registration consistency under S02; retain schema validation and conflict detection. A shared compiler/OpenAPI parameter plan is a later design candidate, not an added patch abstraction. |
| Security helpers | No additional deletion justified. Bearer parsing is already shared; extraction and actual authentication must remain distinct. |
| Lifecycle / WebSockets | Retain Starlette integration, yielded state, explicit resolver binding, threadpool execution and shutdown contracts. Check middleware changes across all protocols. |
| Background / streaming / files | Retain response-before-task-before-file-cleanup ownership and cancellation handling. These layers protect recent fixes and are not dead weight. |
| Cache | Retain bounded storage and explicit app isolation; no Redis/Memcached removal justified. No live external backend service was exercised in this assessment. |
| Example | All example tests pass. Remove only demonstrated unused configuration/members in separate changes; preserve the tested auth, KYC and notification flow. No example deletion budget is proposed. |
| Tests | Preserve behavior regressions. Historical filenames may be reorganized later, but repeated themes do not prove duplicate coverage. Add checks for demonstrated missing cases rather than rewriting the suite. |
| Benchmarks | Keep ASGI microbenchmarks, network benchmarks and endurance tests as distinct measurement boundaries. Reuse shared scenarios/server selection; do not merge unlike metrics into a capacity number. |

## Suggested 1.4.3 sequence

1. **Correctness and repeatability:** resolve middleware order/state (S01), docs
   collisions/setup consistency (S02) and supported environment checks (S10).
2. **Bounded removals:** unused members (S03), unreachable error code (S04),
   duplicated response mechanics (S05), overlapping body checks if proven safe
   (S06), and the fake optional cache import (S09).
3. **Measured DI experiment:** investigate S07 on an isolated branch. Accept only
   if it removes repeated work without relaxing override/lifetime checks. It
   does not block release if the safe simplification is not ready.
4. **Optional CORS delegation:** evaluate S08 independently with explicit
   compatibility decisions. Defer S11/S12 restructuring by default.

Each item should be independently reviewable and reversible. This initial
assessment preceded the authorized 1.4.3 implementation; the evidence index
records the resulting version/runtime changes.

## Acceptance evidence for implementation

Run the affected existing contracts and a small reproducer for each confirmed
defect, then the complete package/example suite once the candidate is ready.
Validate supported Python 3.10–3.13, wheel and sdist installs outside the checkout,
and actual target platforms. Preserve the same response bodies, headers, status
codes and lifecycle ownership unless a specific correction is documented.

Compare baseline/candidate with the same interpreter, resolved dependencies,
server and workloads. Interleave repeated runs; retain raw results. Measure
async and sync/threadpool scenarios separately, including DI graphs, large
route sets, body failures, middleware, streaming and disconnects. Network tests
should retain per-scenario p95/p99 and error counts; load/rest cycles should
sample RSS and open descriptors. Require zero incorrect responses and no
unexplained resource growth within the tested interval. Agree numeric
performance budgets before calling a result acceptable; none is invented here.
